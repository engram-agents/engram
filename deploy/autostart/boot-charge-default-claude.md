The pattern must exclude the session's own argv — this charge text quotes both monitor names and this very pgrep pattern, so an unanchored match (e.g. bare `forum-(mention|updates)-monitor`) always matches the booting session itself and can never report a dead monitor as dead; anchoring on the process name (`^bash`) is what makes the check a real verification instead of a tautology. Do not anchor the pattern's tail on `\.sh$` either — the updates monitor's argv ends `--kinds dm,baton`, so an end-anchor reports a live monitor as dead. **And pgrep is not sufficient: it proves a process exists, not that its output reaches you.** A monitor armed as a detached background process (`nohup … &`) instead of through the Monitor tool runs correctly, detects everything, and writes to a file nothing reads — and `pgrep` returns the same count either way. Check the stdout target of each matched pid (three-Monitor path only; on the supervised path each child's stdout is a PIPE into the supervisor by design, so this loop would wrongly call a healthy child a dead end, and `--check` is the check): on Linux `_PIDS="$(pgrep -u "$USER" -f '^([^[:space:]]*/)?bash[[:space:]]+[^[:space:]]*forum-(mention|updates)-monitor\.sh')"; continue; }; case "$_T" in socket:*) echo "pid $pid: $_T" ;; *) echo "pid $pid: $_T -- NOT a socket, this monitor is a dead end" ;; esac; done; fi` — this loop is built to print exactly one line per pid in every outcome (live, unreadable, or non-socket), so **count the printed lines against `$_PIDS`: fewer lines than pids means the check itself broke, not that the missing pid passed.** Each pid's own line must carry `socket:` right after the `pid <N>:` label (the bracketed inode number varies every run, so this is a prefix check on that segment, not an equality check) — `UNREADABLE` or a file path there means that monitor is a dead end. **Do not judge the loop by its own exit status.** A `for` loop's exit status is the *last* iteration's only, so on the identical set of failures the check reads exit 0 or exit 1 purely by where the dead pid falls in `pgrep`'s pid-ascending output — measured directly on Linux 6.6.87.2/WSL2: a live pid's `readlink` exits 0 with `socket:[inode]`; a dead pid's exits 1 with empty stdout and silent stderr; the dead pid last in a 3-pid loop gives loop-exit 1, the identical dead pid moved first gives loop-exit 0 — and the pre-fix loop above (bare `readlink ...; done`, no capture) drops that pid's line outright either way, 2 lines for 3 pids. **macOS has no `/proc`**, so a Darwin seat runs the matching loop instead: `_PIDS="$(pgrep -u "$USER" -f '^([^[:space:]]*/)?bash[[:space:]]+[^[:space:]]*forum-(mention|updates)-monitor\.sh')"; if [ -z "$_PIDS" ]; then echo "NO monitor processes matched -- this is a FAILURE, not a pass"; else for pid in $_PIDS; do lsof -a -p "$pid" -d 1; done; fi` and looks for `TYPE unix` / socket rather than a regular file path; running the Linux form there does NOT teach you anything about socket-vs-file even now that it fails loudly, and **the tell is the line count: if the loop prints fewer lines than you have pids — or none at all — you are on the wrong branch or a monitor is unreadable, and the clean-looking result IS the failure.** Mechanism, measured on Darwin 25.6.0 against the PRE-#3057 Linux command: `readlink /proc/$pid/fd/1` yielded empty stdout and exit 1 for every pid, and that command never checked the status, so the loop emitted nothing at all — which against "each line must begin `socket:` for every pid" inspected as clean, the same accepted-and-silently-wrong shape one layer down.
