## 2. The ledger — one row per matching line (row 55 holds two connects; rows count lines, not connects)

Columns. **kind:** `call` or `prose`. **target:** `live store` (the seat's `$ENGRAM_HOME/knowledge.db`), `parameter` (path passed in; live callers named), `other DB` (named). **access:** the open mode — `ro` is `mode=ro`; `rw` means opened without `mode=ro` (a read-only use is said in the note). **state** (live-store rows only): `owner` · `direct` · `behind-flag` · `flag-on` · `retired`. **A6 delta:** the user-identity and stop rows have one. **macOS:** per row, for every live-store row; `no Mac launcher yet (#3709)` = the owner's own connection, or a channel with a planned owner path; the owner can start on a Mac (#3703), and nothing launches it there yet, `n/a — no owner path planned yet` = no owner path is planned for this channel (see the Mac seats paragraph).

**Mac seats, applies to every `macOS` cell below.** Since #3703 (the Darwin permission arm, closes #3666) the owner can start on macOS: `platform_unsupported_reason()` has a Darwin branch (`socket.LOCAL_PEERCRED`, `/bin/chmod`, `/dev/fd`). But neither U5 launch path starts it there yet: the SessionStart fallback (`start-engramd-owner.sh`) launches nothing on macOS and `setup-surface-daemon-service.sh --owner` refuses (#3709). So the two `*_via_owner` flags in tree today, `engramd.user_identity_reads_via_owner` (U4d) and `engramd.stop_reads_via_owner` (U6a), have no effect on a Mac seat except to make their hook report `Unavailable`; U6b's flag (`engramd.lesson_tripwire_reads_via_owner`) is not in tree yet, and once it exists it would behave the same. This holds until a Mac launcher lands (**#3709**). Per #3666 the affected seats are Aleph, Clio and Luria.

## 6. Owner writes — the closed write set (U11, #3822 Stage A)

The owner's first write. Design: `docs/2652-engrammanager-design.md` §3.1 (typed writes, never a generic `write_sql`) and §5.4 (read-back acknowledgement and idempotency key). **Stage A is the owner op; its one caller (Stage B) is the "Caller" line below.**

- **The op:** `use_reward`, params exactly `{node_ids, action, request_id}`. `action` is a closed enum, today `{"mention"}`. The client supplies no alpha, no config path and no value: alpha is `engram_restamp.USE_ALPHA[action]`, owner-side. Any extra key is rejected as an unknown param (`use_reward_params_shape`), never ignored.
- **Closed write set:** `{use_reward}` (`engramd_owner.WRITE_METHODS`, pinned by a test). Every method in the owner's table carries a kind, `read` or `write`; a method with no kind is default-deny at dispatch (`method_kind_missing`), and a kind that disagrees with the write set is refused (`method_kind_mismatch`).
- **Caller (Stage B, #3822):** `hooks/claude/engram-utility-credit-mention-stop.py` `bump_utility`, behind `engramd.utility_credit_writes_via_owner` (default OFF; read only through `engramd_owner_flags.flag_on` over the hook's module-level `CONFIG_PATH`). Stage A must merge before that flag goes ON anywhere. Row 39 of Section 2 is `behind-flag`: with the flag ON the hook never opens the store and never reaches its WAL pragma. It sends exactly `{node_ids, action: "mention", request_id}` (a fresh uuid4 per fire; no alpha, value or config path) and returns the count `bumped`; an explicit alpha is refused. **Outcomes, in different words:** DETERMINATE not-applied (`Rejected(busy)`, any other `Rejected`, `Unavailable` other than timeout/protocol) is `bump_utility failed: owner busy (not applied)` / `owner rejected: <reason>` / `owner unavailable (reason=<code>)`, never retried; `Rejected(unknown_operation)` (an older owner) is a specific contract-skew line (restart or upgrade the owner); `readback_mismatch` is `bump_utility committed but unverified` (may have been applied once, do not repeat blindly); INDETERMINATE (`Unavailable` timeout/protocol on a write) is retried ONCE with the SAME `request_id` (the owner's dedupe answers `duplicate`, no second bump) and, if still unanswered, logged `bump_utility indeterminate: owner did not answer (may have been applied once)`, never as "failed". **Once the first attempt was indeterminate, EVERY non-Ok outcome of the retry (`busy`, any other `Rejected`, any `Unavailable`, an unusable answer) is also reported as indeterminate, `bump_utility indeterminate: <reason code>; the first attempt may have been applied once`, never as "not applied" or "failed"** (the first attempt may still hold the owner's lock or already have committed, so a retry's `busy` says nothing about it); `readback_mismatch` stays "committed but unverified" wherever it occurs. "Not applied" is reserved for outcomes of a first attempt. No outcome falls back to the store. Time: the Stop hook is registered with timeout 5 s; both attempts together wait at most 3.5 s, leaving 1.5 s for the rest of the hook. This arithmetic assumes the client's `timeout` bounds each attempt end to end (the `engramd_client.write` docstring says it does; overshoot was not measured). Worst case with the real constants (`engramd_client.OWNER_WRITE_CLIENT_TIMEOUT` 2.0 s, imported by name, no copy in the hook): attempt 1 waits 2.0 s, the retry min(2.0, 3.5 - 2.0) = 1.5 s, total 3.5 s; the retry is skipped if less than 0.25 s of the budget is left. The owner's own lock wait is 1.0 s, so a typed `busy` arrives well inside attempt 1 and is never retried. Pinned in `tests/test_utility_credit_owner_write_3822.py`; a real-owner cell holds the store's write lock externally and shows the busy line, no retry, nothing bumped.
- **What it runs:** the SHARED `engram_restamp.use_reward` (bump, then the restamp in its own SAVEPOINT), once, on the owner's own connection, in one transaction, under `_owner_lock`. One definition of the Q-update and of the restamp; the owner re-implements neither.
- **Read-back (§5.4), status: built, with stated limits.** The op reads `(utility_score, importance_score, recall_turn)` of each updated id inside the write transaction (the in-transaction values), COMMITs, re-reads the same three columns from the committed store (the committed values), and returns `ok` only if they are equal and an independent monotone invariant holds. A mismatch returns `Rejected(readback_mismatch)` naming the id(s), with `commit = "committed_unverified"`: **the commit cannot be undone at that point**, so the state is "committed but unverified", reported loudly and recorded so a replay re-reports it instead of bumping again. **What it CAN detect:** a COMMIT that did not apply; another connection committing to the row between this COMMIT and the re-read; and a shared function that claims an update (`bumped > 0`) without moving a utility that was below 0.99 (the monotone invariant: each id's `utility_score` is read inside the transaction BEFORE the shared call, NULL as 0.0, and the committed value must be strictly greater; the detail says `write did not land`; ids at 0.99 or above are exempt because 6-dp rounding near 1.0 may leave the value unchanged, and the parity cells own that region). The phase order is pinned: the in-transaction read runs with `in_transaction` True and the re-read after COMMIT with it False. **What it CANNOT detect:** storage-level corruption (the re-read uses the same connection and page cache), and an in-transaction side effect that moves the value plausibly (the in-transaction values are observed state, not a recomputation). The owner does not independently know what the write meant: the Q-update lives in the shared function, and the read-back checks that its effect is present and consistent, not that it is the right number. Probe P1 (the shared bump and restamp replaced by fakes that write nothing) is a cell and is refused.
- **Ack fields (`ok`):** `updated` (ids actually updated, first-occurrence order, duplicates collapsed, missing ids skipped), `bumped`, `restamped`, `restamp_error` (None, or the shared function's `config: ...` / `restamp: ...` string), `rows` (`{id: {utility_score, importance_score, recall_turn}}`, the committed values), `duplicate`. A bump committed with the restamp failing is an `ok` ack with `restamp_error` set and `restamped = 0`; it still reads back (utility moved, `recall_turn` unchanged).
- **Idempotency, and its stated bound:** `request_id` (client-generated, non-empty, at most 128 UTF-8 bytes) dedupes the whole op (bump and restamp together). The same id twice is `ok` with `duplicate = true` carrying the first result; the same id with a different payload is refused (`use_reward_request_id_reused`); the payload is held as a 32-byte SHA-256 of its canonical encoding, never as the ids (a 500 x 256-byte payload would otherwise cost ~128 KB per entry). The dedupe store is in memory and LRU-bounded (`USE_REWARD_DEDUPE_CAP = 1024`). **Known bound:** it dies with the process, so an owner restart between COMMIT and ack followed by a client retry can double-bump, and past the cap the oldest id is forgotten. For this op that is a small monotone over-credit (Q only moves toward 1.0), not corruption. A persisted dedupe table is a schema change and out of scope by the design seat's call. Pinned by `test_KNOWN_BOUND_an_owner_restart_forgets_request_ids_so_a_retry_double_bumps`. The wire-level `request_id` the client library adds is separate and unused for dedupe; the dedupe key is the one inside `params`.
- **Config-read parity:** the owner reads the `memory` block of its own `ENGRAM_HOME/config.json` on every call (never cached at start; `current_turn` moves at sleep), through the same `engram_restamp.read_memory_config` the hook uses. An absent file or one with no `memory` block yields the defaults (turn 0) on both paths: not an error. A torn file, a FIFO or a directory yields `restamp_error` with the bump standing, on both paths. Cells pin each on both paths.
- **The closed statement list** (pinned by a trace-callback test; red if the shared function also writes anything else): `SELECT utility_score FROM nodes WHERE id = ?`; `UPDATE nodes SET utility_score = ? WHERE id = ?`; `SELECT importance_base, recall_count FROM nodes WHERE id = ?`; `UPDATE nodes SET importance_score = ?, recall_turn = ? WHERE id = ?`; the read-back `SELECT utility_score, importance_score, recall_turn FROM nodes WHERE id = ?`; `BEGIN IMMEDIATE` (the op opens its own write transaction up front, so the pre-op reads are inside it), `COMMIT`, `SAVEPOINT engram_use_restamp`, `RELEASE SAVEPOINT engram_use_restamp` (plus `ROLLBACK TO` on a failed restamp or an aborted op), and the op's own busy-wait bracket, `PRAGMA busy_timeout` (read the prior value) and `PRAGMA busy_timeout = N` (set 0, then restore), which run under the permissive authorizer just outside the allowlisted window.
- **The authorizer swap SUPERSEDES the security design's no-swapping clause, for `_owner_conn` only, and why that is acceptable.** `docs/2652-security-slice-design.md` §3.1 decided, with its stated reason, "client-read connection permanently restrictive; no authorizer swapping". That ruling stands for `_client_read_conn`, which is never swapped. For `_owner_conn` this unit supersedes the clause: the connection starts permissive and the op installs a restriction for its duration. **Polarity, from the code:** the failure the clause feared was "left permissive, the floor is gone". Here the install runs the other way. If the `finally` failed to put the permissive authorizer back (only `set_authorizer` itself raising could do that), the op's restrictive guard would stay installed, so later owner-internal SQL on `_owner_conn` would be DENIED, loudly: it fails closed, not open. It is not silent. A separate, smaller failure: the same `finally` restores `PRAGMA busy_timeout` after the authorizer; if only that restore failed the connection would keep `busy_timeout = 0` (immediate BUSY instead of waiting), also loud and not permissive. **Residual:** the swap window is safe only because (1) every user of `_owner_conn` holds `_owner_lock` (the op holds it for the whole swap), and (2) the other user, snapshot's `backup()`, never consults an authorizer at all (the measured, load-bearing surprise in the module docstring), so nothing there is denied or widened. Both rest on facts a test in this build can pin only indirectly: a cell runs a snapshot after an ok, a denied, a raised and a busy `use_reward`. Any future owner-internal SQL added inside or around a `use_reward` call would be denied by the op allowlist and would look like a bug in that new code.
- **Trigger disjointness is pinned as a property, not a name list.** A cell parses the real schema's triggers on `nodes` from `sqlite_master.sql` (a plain `UPDATE ON nodes` with no `OF` list counts as firing on every column) and asserts {columns `use_reward` writes} and {columns any trigger on `nodes` fires on} are disjoint; scratch triggers that couple them turn it red. The by-name pin of the 7 triggers stays as the second line.
- **Transaction hygiene and displacement.** On any exit, `BaseException` included, the shared connection's transaction is rolled back before the exception propagates (a leaked open transaction would otherwise be committed by the next op); an op refuses to start (`use_reward_txn_open`) if the connection already has a transaction open. The connection changes (busy timeout, then authorizer) sit inside ONE `try/finally` opened before the first of them; each restore has its own inner `try`, so a failing restore of the permissive authorizer cannot skip the busy-timeout restore (the guard admits exactly `PRAGMA busy_timeout` for that one restoring statement, since the restrictive authorizer would otherwise deny it). `engram_walguard.assert_not_displaced` runs a second time under `_owner_lock`, before the transaction, since the dispatch-time check can be stale by the whole lock wait; the rejection is the same `substrate_displaced`.
- **The internal authorizer, stated exactly:** `_owner_internal_authorizer` stays permissive (`SQLITE_OK` for everything) and is NOT a security boundary; it still serves snapshot's `.backup()` (which never consults an authorizer) and cleanup. For `use_reward` only, a RESTRICTIVE allowlist authorizer is installed on `_owner_conn` before the transaction opens and the permissive one is restored in a `finally` on every exit path, all under `_owner_lock`. It is column-exact (reads of `nodes.{id, utility_score, importance_base, recall_count, importance_score, recall_turn}`; updates of exactly `utility_score`, `importance_score`, `recall_turn`; the transaction codes; the one savepoint named `engram_use_restamp`), and a COMMIT or ROLLBACK issued from inside the shared function is denied (they belong to the handler's own phases). A statement that originates in a trigger is admitted only if that trigger is named in `USE_REWARD_ADMITTED_TRIGGERS`, which is empty: the real schema has 7 triggers on `nodes` (pinned against `sqlite_master` by a test) and none fires on those three columns (measured). **Any denial refuses the whole op** (`write_denied`, rolled back, no partial bump), including a denial the shared function's restamp guard would otherwise absorb as `restamp_error`. The bound is therefore: fixed statements + the statement-set pin + this allowlist + the 8b to 8d cells.
- **Contract version:** `CONTRACT_VERSION` 1.1 to 1.2. `check_contract_version` tolerates MINOR skew, so the new method is additive. An older (1.1) owner answers `use_reward` with `Rejected(unknown_operation)`, which the client returns typed; Stage B's hook must make that loud.
- **Wait budget and `busy` (fold 1):** the server and hooks also write the store directly, so the op may have to wait. The TOTAL wait is one named budget, `engramd_owner.OWNER_WRITE_LOCK_WAIT = 1.0 s`: the `_owner_lock` acquire and the wait for a competing direct writer share it. When it runs out the op answers `Rejected(reason="busy")`: determinate, nothing committed, rolled back, **not** recorded for dedupe (a retry runs). `busy` is the one reason for "could not get the lock in time" (the lock acquire and the store's write lock alike); any other `sqlite3.Error` stays `use_reward_write_failed`. The budget is pinned by a test to be strictly less than `engramd_client.OWNER_WRITE_CLIENT_TIMEOUT (2.0 s) - OWNER_WRITE_REPLY_RESERVE (0.5 s)`, so the refusal arrives before the client gives up (the 0.5 s reserve is a judgement, not a measurement). **Mechanism:** SQLite's own busy handler is switched off for the op (`PRAGMA busy_timeout = 0`, set while the permissive authorizer is installed because the op allowlist denies PRAGMA, and restored to its prior value in the same `finally` as the authorizer) and the owner retries the whole transaction every 20 ms until the budget is spent. Measured on macOS, SQLite 3.53.4, Python 3.12: SQLite's busy handler overshoots its timeout (`busy_timeout = 1000 ms` waited 2.4 to 2.6 s; 300 ms waited about 1.2 s; `connect(timeout=)` behaves the same), so it cannot carry a bound a client deadline sits on. With the retry loop a 1.0 s budget measured 1.08 s. Not measured: other platforms or SQLite builds.
- **The one indeterminate case:** the client's own timeout. An `Unavailable` with reason `timeout` or `protocol` on a WRITE is INDETERMINATE (the op may have committed before the reply was lost), never "failed". The remedy is ONE retry with the SAME `request_id`: the dedupe store answers with the stored outcome, `duplicate = true`, without a second bump (pinned by a cell that commits, stalls the reply past the client timeout, and retries). `engramd_client.write()` says so in its docstring. A `Rejected` on a write is determinate only up to the COMMIT (nothing committed before it); `readback_mismatch` (`commit = committed_unverified`) is the one refusal that comes after it. Any failure after the COMMIT, a verification bug, `MemoryError` or a `BaseException` included, is recorded in the dedupe store as that same committed-but-unverified outcome BEFORE it propagates (an `Exception` is returned to the client as that typed rejection, never as a bare `internal_error`; a non-`Exception` is re-raised after recording, with the lock, authorizer and busy timeout still restored), so a same-`request_id` retry replays it and does not bump again. "Recorded before anything propagates" holds except where `record()` itself fails (practically only `MemoryError` in its deep copy): then nothing is recorded and a same-`request_id` retry would bump again. The `record(response)` on the ok path has the same exposure (pre-existing). **Obligation carried forward:** the owner's wait budget is tied to the owner's request deadline, never to the client's own timeout, so "the refusal arrives before the client gives up" holds only if the caller passes `OWNER_WRITE_CLIENT_TIMEOUT` as its timeout. Stage B's hook is the caller that must (it imports the constant, and a cell there pins it). `Rejected(busy)` here is a different thing from the client's `Unavailable(reason="busy")` (a full accept backlog: the request was never delivered) and from the owner's snapshot `Rejected(busy)` (finalize slots full): all three mean "not done, retry", and none is confused in code or tests (the client maps owner rejections by type, and no caller branches on a bare `busy` string).
- **Read-scan gate:** the op registers no read template and adds no `sqlite3.connect(` line, so Sections 2 and 3 and `engramd_read_templates.json` are unchanged.

### The second write: `advance_moment_cursor` (U13, #3856)

The last hook-side direct site and the owner's second write. It replaces two copies of a read-modify-write of the WHOLE metadata dict (the surface hook and `engram_query`, both lossy against a concurrent `engram_update_person` / `engram_add_special_moment`) with ONE shared compare-and-set statement, so it fixes the race at the root instead of porting it.

- **The op:** `advance_moment_cursor`, params exactly `{person_id, from_cursor}`. `from_cursor` is an int in `[-(2**53), 2**53)`, not a bool; `person_id` a non-empty string of at most 256 UTF-8 bytes. Any extra key (`request_id` included) is rejected as an unknown param (`advance_moment_cursor_params_shape`), a missing key too; the owner computes the target (`from + 1`), the client sends no value to write. Hostile values are refused before any statement runs (a trace cell asserts zero statements).
- **Closed write set, now `{use_reward, advance_moment_cursor}`** (`engramd_owner.WRITE_METHODS`, pinned by a test; kind `write`; the read set is unchanged).
- **No `request_id`, and why:** the statement is a compare-and-set (`... AND <stored cursor under the one rule> = :from`). A replay is harmless by construction: a retry after COMMIT finds `from + 1` and answers `stale` with that value, so no dedupe store is needed (`use_reward`'s bump is not idempotent, which is why it has one). A client timeout on this write is therefore indeterminate but cheap: the caller may retry once with the SAME `from_cursor`, and `stale` carrying `from + 1` means the first call landed.
- **What it runs:** the SHARED `engram_moment_cursor.advance_moment_cursor` once, on the owner's connection, under `_owner_lock`, after `BEGIN IMMEDIATE`; COMMIT only when it applied, ROLLBACK otherwise. The ack is `{applied, cursor, reason}`: `stale` / `not_person` / `not_object` are typed ANSWERS (`status ok`, `applied: false`), not refusals. The cursor rule (an int, not a bool, in the window, else 0) is defined once in `engram_moment_cursor` and used on both the Python and the SQL side; a stored `true`, a string, a float or a value outside the window reads as 0 on both.
- **The authorizer allowlist, MEASURED** (authorizer-recorded over real runs of the shared function on the real schema: applied, stale, not_person, not_object, and the read-back SELECT; pinned as `MEASURED_TUPLES` in `tests/test_engramd_moment_cursor_3856.py`, and the live owner run is checked to be a subset): `TRANSACTION` BEGIN / COMMIT (ROLLBACK from the handler's own abort path); `FUNCTION` `json_set`, `json_valid`, `json_type`, `json_extract`; `READ` of `nodes.metadata`, `nodes.id`, `nodes.type`, `nodes.is_current` (db `main`); `UPDATE` of `nodes.metadata` only; plain `SELECT`. **The guard-trigger entry:** `nodes_metadata_json_guard_update` (`BEFORE UPDATE OF metadata`, `WHEN NEW.metadata IS NOT NULL AND NOT json_valid(NEW.metadata)`) fires on every metadata update, so its tuples appear in the trace at prepare time even for a statement that matches no row: `READ nodes.metadata`, `FUNCTION json_valid` (it arrives through the trigger's WHEN clause and body, not through the op's own statement) and `SELECT`. `RAISE(ABORT)` itself needs no authorization code (an invalid-JSON write under the allowlist raises the trigger's own error with zero denials). A statement originating in a trigger is admitted only if the trigger is in the named allow-set. Everything else (INSERT, DELETE, other columns or tables, PRAGMA, SAVEPOINT, DDL, other functions) is denied, and a COMMIT or ROLLBACK from inside the shared function is denied (they belong to the handler's phases).
- **The trigger allow-set property, and why it replaces U11's disjointness.** U11 pinned `{columns use_reward writes}` disjoint from `{columns any trigger fires on}`. That property is FALSE here by construction: the metadata JSON guard fires on every metadata update. So the property is a named allow-set: a cell parses the real schema's triggers on `nodes` from `sqlite_master` (an UPDATE trigger with no `OF` list, or an `OF` list containing `metadata`, handling quoting and case, including the dynamically built `nodes_fts_rewrite_resync` whose column list is the live FTS column set), checks the parse against the ground truth (which triggers the prepared statement actually compiles in), and requires the result to equal `MOMENT_CURSOR_ADMITTED_TRIGGERS` = `{nodes_metadata_json_guard_update}`. A NEW trigger on `metadata` turns it red; the answer is a report to the design seat, never widening the allow-set to pass.
- **Read-back (§5.4), with its stated exposure:** after COMMIT the op re-reads the person's cursor from the committed store under the same rule and compares it with the rule applied to `from + 1`; a disagreement is `Rejected(readback_mismatch)` with `commit = "committed_unverified"`, and any failure after the COMMIT (an `Exception`, or a `BaseException` after recording nothing to lose) lands there too. **Exposure, same class as U11's:** the owner lock does not exclude a direct writer (the flag-OFF hook, the server), so a direct advance landing between the COMMIT and the read-back reads as `readback_mismatch` although both advances are real. The reply says not to repeat blindly and to read the current cursor. At `from = 2**53 - 1` the stored `2**53` is outside the window and reads as 0; the comparison uses the rule on both sides, so that edge is a verified commit.
- **One budget for all owner writes (rename, one commit of its own):** `USE_REWARD_LOCK_WAIT` is now `engramd_owner.OWNER_WRITE_LOCK_WAIT` (1.0 s) and `USE_REWARD_CLIENT_TIMEOUT` / `USE_REWARD_REPLY_RESERVE` are `engramd_client.OWNER_WRITE_CLIENT_TIMEOUT` (2.0 s) / `OWNER_WRITE_REPLY_RESERVE` (0.5 s); values unchanged, no alias. The scaffold (lock acquire, displacement re-check, open-transaction refusal, busy-timeout switch, authorizer install and restore) is one definition, `EngramdOwner._owner_write`, which both ops run through.
- **Contract version:** `CONTRACT_VERSION` 1.2 to 1.3, minor and additive. An older owner answers the op with `Rejected(unknown_operation)`; the hook makes that loud (see below).
- **Caller (phase 3):** `hooks/claude/engram-surface-hook.py` `_advance_person_moment_cursor`, behind `engramd.surface_writes_via_owner` (default OFF; read only through `engramd_owner_flags.flag_on` over the module-level `CONFIG_PATH`; independent of the reads flag; a helper that raises reads OFF and its class name is reported under `surface-owner-flag`). Flag ON: the advance goes ONLY to the owner via `write("advance_moment_cursor", {person_id, from_cursor})`, zero direct connects, no fallback on any non-Ok outcome. It returns True only for Ok with `applied` true; `stale` / `not_person` / `not_object` are quiet Falses; Unavailable, Rejected and a client import failure are False AND recorded loud (the first per fire) under the existing `surface-owner` notice kind, rate-limited by the shared probe-notice stamp. `Rejected(unknown_operation)` says the owner is older than the hook (contract skew), the cursor was NOT advanced and the owner needs a restart or upgrade; `readback_mismatch` and a timeout say the cursor MAY have advanced. **One attempt, no retry:** a lost advance only means the same moment may repeat sooner. Time: the hook's registered timeout is 10 s and the write follows the render, so the call gets `min(10 - 1.5 - elapsed, OWNER_WRITE_CLIENT_TIMEOUT)` (no call below 0.25 s left); owner time is at most 3.0 s of reads + 1.0 s ping + one write of at most 2.0 s, and after the first owner failure the fire makes no further owner write.
- **Bound of the parity claim, and three corrupt-row classes that fail safe.** "The SQL predicate agrees with the Python rule" holds for **every value `json.dumps` can emit**, not for every byte string a legacy row might hold. Three classes of corrupt row are read differently by `json.loads` and SQLite (measured on SQLite 3.53.4): (a) **duplicate keys**: Python keeps the last, SQLite the first (`{"special_moment_cursor":1,"special_moment_cursor":2}` reads 2 vs 1; `{"special_moment_cursor":"x","special_moment_cursor":7}` reads 7 vs 0); (b) an **escaped key spelling** (`"special\u005fmoment_cursor"` is the cursor key to Python and overrides the plain one: 8 vs 4); (c) **`NaN`** in the blob (Python parses an object, SQLite's `json_valid` says no, so the row answers `not_object`). They are deliberately NOT reconciled. Each fails in the safe direction: the callers send the Python-side value, the statement compares the SQL-side one, so the advance answers `applied: false` (`stale`, or `not_object`), the row is byte-unchanged, nothing raises, and the moment repeats; one cell pins exactly that. Every `json_*` call in the cursor expression and the object test reads the column through the #3485 wrap (`CASE WHEN json_valid(metadata) THEN metadata END`; #3865 replaced the earlier nested `CASE WHEN json_valid(metadata) THEN <cursor expr> END`), so a malformed legacy row can never reach `json_type` / `json_extract` (which raise `malformed JSON`) whatever order SQLite evaluates the ANDs in, and the one expression is self-guarded (safe alone); the object test is then the only term excluding a non-object row; `json_valid` was already in the allowlist, and the measured authorizer tuples are unchanged.
- **Notice priority, stated:** when a read failure and a write failure occur in the SAME fire only the read failure reaches `_pending_owner_notice` (the write failure reaches stderr only: `owner write failed: <kind>`).
- **A missing cursor module is loud, not a silent stuck rotation:** if `engram_moment_cursor` cannot be imported by the surface hook, the cursor reads 0 and the advance returns False, so the same first moment would render forever; every fire that selects a person moment in that state writes one stderr line (`moment cursor module unavailable: the rotation will not advance`) and adds one notice per window under the NEW kind `surface-moment-cursor` through the same shared probe-notice stamp (no second mechanism); everything else stays best effort.
- **Surviving direct callers:** the flag-OFF hook path (the shared function on the hook's own RW connection) and `engram_query._select_and_render_person_moment` on the server's own connection, which migrates last (design §6). Both now run the shared statement, so the race is gone on every flag value.
- **Read-scan gate:** the hook function no longer holds a SQL literal, so the registered template `SELECT metadata FROM nodes WHERE id = ?` and the site `_advance_person_moment_cursor` left `engramd_read_templates.json` in phase 1; the `sqlite3.connect(` line count is unchanged.
